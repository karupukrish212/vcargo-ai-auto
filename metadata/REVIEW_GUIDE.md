# Manual business metadata review for vcargo

Edit the YAML files below in your IDE. The existing MySQL tables and column types
remain unchanged. `generated/schema_raw.json` records technical facts and is
regenerated by extraction; put human descriptions and decisions in the YAML
files instead. The metadata loader does not connect to MySQL or execute SQL.

## 1. Choose report scope first

Edit [policies/table_scope.yaml](policies/table_scope.yaml):

```yaml
excluded_patterns:
  - '*seq'
  - 'driver'
excluded_tables:
  - comments
  - email_otp
  - responsibility
  - role
  - rolepermission
  - rolepermissionheader
  - roles
  - rolesresponsibility
  - screenname
  - screens
  - tdriverdocuments
  - token
  - tvehicledocuments
  - user_action
  - userbranchaccess
  - userrolesaccess
  - vehicle
preferred_tables:
  - tdriver
  - tvehicle
```

These exclusions reflect your instructions. The 33 `*seq` tables plus the 17
explicitly excluded tables are outside report scope, leaving 21 tables eligible
for review. Existing YAML files for excluded tables are retained, including
role/screen/token tables and `email_otp`. All 71 tables remain in the raw catalog
and ERP.
The requested `tokens` table is named `token` in the extracted catalog.
`tdriver` and `tvehicle` remain preferred and in scope. You do not need to describe excluded
tables for current reports. When a table is needed for RBAC or another future
feature, remove its exact name from `excluded_tables` and review its metadata
before including it. Removing an exclusion does not automatically verify it.
Add other unwanted tables to `excluded_tables` using their exact names; remove
a name/pattern if that table becomes relevant. `preferred_tables` is a ranking
hint for the future retriever, not permission to use an unverified table.

There is no table named `driver` in the extracted snapshot. The exact-name
pattern `driver` excludes that legacy table if it is added later, while keeping
`tdriver` in scope. `trip.driver` is a
column with a physical FK to `tdriver.tdriverid`. Keep that column available for
verified joins. `tdriverdocuments` and `tvehicledocuments` are currently excluded;
their YAML files are retained for future review.

## 2. Describe the important tables

Start with [tables/tdriver.yaml](tables/tdriver.yaml) and
[tables/tvehicle.yaml](tables/tvehicle.yaml). Both tables have reviewed reporting
columns; local drafts remain unavailable until reviewed. `tvehicle.pickuplocation`
is explicitly excluded because the project owner confirmed it was created in error.
The current column review also covers `trip`, `customer`, `tripinvoice`,
`tripinvoiceitem`, `users`, and part of `maintenance`: eight tables and 189
approved columns in total. Maintenance has 24 approved columns; its costs use
INR, its odometer reading uses kilometres, and its status/priority/type codes
are confirmed. Only its branchcode and branchname remain drafts.
The [first report definitions](REPORT_REVIEW.md) now record the approved
questions, date/filter rules, and missing-value and balance rules. Next are SQL
examples and expected-result checks. You do not need to finish all 21 in-scope tables before building a small,
reviewed reporting scope. Review additional tables when a requested report needs
them. Skip the driver and vehicle document tables while they are excluded.

At the top of each file, fill these fields. This is a draft illustration; adjust
it to the application's actual meaning of one row:

```yaml
table_name: tdriver                    # Preserve the exact SQL table name
business_name: Transport Driver
description: 'Describe exactly what one row represents in your application.'
domain: transport
aliases:
  - driver
queryable: true
verified: false                       # Keep false while reviewing
source: manual
reviewed_by: null
reviewed_on: null
```

`domain` is your grouping label, such as transport, billing, customer, or support.
It groups related business tables for future retrieval; it is not a database
name, internet domain, or access-control rule. For `tdriver`, `transport` is an
appropriate grouping label.
Aliases are names users say, not extra database tables. If a table is unneeded,
set `queryable: false` or exclude it centrally. Do not guess a business purpose
from the table name: in particular, review what `ticket` means in this ERP.

After you have approved a definition, change `verified` to true, use `source:
manual` (or `user_provided` for explicit expert input), and add your name and
review date. For example:

```yaml
verified: true
source: manual
reviewed_by: 'Your actual name'
reviewed_on: '2026-10-09'                # Use the date you perform the review
```

Generated or LLM suggestions cannot be marked verified while their source is
still `schema_generated` or `llm_generated`. The validator rejects that change.
Table verification does not automatically verify any column.

## 4. Review shared flags in one place

Edit [columns/common_columns.yaml](columns/common_columns.yaml). Your explicit
chat confirmation is already recorded there:

| Profile | Stored code | Confirmed meaning |
|---|---|---|
| active_flag | `0` | INACTIVE |
| active_flag | `1` | ACTIVE |
| cancel_flag | `0` | NOT_CANCELLED |
| cancel_flag | `1` | CANCELLED |

Those shared profiles are verified with the confirmation source and date. The
per-table references still start as drafts. To approve a flag column in a table
you have reviewed, retain its profile/encoding and add your review details:

```yaml
columns:
  active:
    profile: active_flag
    value_encoding: numeric
    verified: true
    source: manual
    reviewed_by: 'Your actual name'
    reviewed_on: '2026-10-09'
```

Quote YAML code keys as `'0'` and `'1'` in the shared `values` mapping. The actual
column datatype determines how a future query represents them. `tdriver.active`
and most cancel flags use BIT, so their encoding is `numeric`; `tvehicle.active`
uses VARCHAR, so its generated entry correctly uses `value_encoding: text`.
Do not replace that entry with `numeric` just because the visible values are 0/1.

Shared and local column definitions must both be verified to expose the resolved
column. A local `queryable: true` cannot override a shared `queryable: false`.
If a table has a different meaning for a flag, remove its shared profile and
write an explicit local definition. Do not change the global profile for a
single-table exception.

These meanings do not impose a global `active=1 AND cancel=0` filter. A report
may intentionally count inactive or cancelled records; its reviewed metric or
filter definition must state the intended rule.

### Reuse other common column descriptions

The same shared-profile mechanism covers all ten common column names:

| Column | Shared profile |
|---|---|
| createdon | audit_created_text or audit_created_native |
| modifiedon | audit_modified_text or audit_modified_native |
| createdby | created_by_user |
| modifiedby | modified_by_user |
| active | active_flag |
| cancel | cancel_flag |
| orgid | organisation_reference |
| branchcode | branch_code |
| branchname | branch_name |
| userid | related_user |

Review descriptions once in `columns/common_columns.yaml`, then reference the
appropriate profile under an existing column in each table. For example:

```yaml
columns:
  createdby:
    profile: created_by_user
    verified: false
    source: manual
```

The loader resolves the shared definition and explicit local overrides before
exposing approved columns. Both the shared profile and its local use must be
reviewed. Empty local descriptions override the shared text, so omit description,
business_name, and aliases when you want to inherit them. Keep datatype-specific
encodings and table-specific exceptions in the table file. Keep logical joins
in `relationships/logical_relationships.yaml`; a shared description does not
create a foreign key.

Only reference columns that exist in the raw schema. A table without `userid`
does not need a `userid` entry, and the loader will not add one. The project owner
confirmed the shared audit dates, creator/modifier user references, and the
`orgid` reference to `users.userid`. Branch and related-user profiles remain
drafts until their meanings are confirmed. Newly generated templates reference
these profiles automatically. Blank draft entries in existing files also use
shared references; expert-reviewed descriptions are preserved. Convert reviewed
entries to shared references as you review each table, retaining local exceptions.

## 5. Describe string dates without changing their database datatype

The supplied example `19-09-2026 03:29:13 PM` corresponds to this MySQL format:

```yaml
date:
  storage: text
  mysql_format: '%d-%m-%Y %h:%i:%s %p'
  timezone: Asia/Kolkata
  invalid_value_policy: fail_closed
```

The shared text-date profiles already contain the format and your confirmed
India timezone. `%h` is the 12-hour hour, `%i` is minutes, and `%p` is AM/PM.
The future query compiler can use MySQL's
[STR_TO_DATE function](https://dev.mysql.com/doc/refman/8.0/en/date-and-time-functions.html#function_str-to-date)
with this reviewed format. This metadata milestone does not implement query
generation or date-based report execution yet.

In the actual catalog, the common audit names are `createdon` and `modifiedon`,
not `updatedon`. Native exceptions exist: `notification.createdon` and
`tdriverdocuments.uploadedon` are DATETIME, while fields such as `trip.startdate`
are DATE. Native date columns use `storage: native` without `mysql_format`.
The templates choose text/native profiles from the extracted type and the
validator rejects an incompatible profile.

Review the shared description and `semantic_type` before marking each date
profile verified. Confirm that `createdon` means record creation and `modifiedon`
means record modification, including exceptions. Then approve relevant local
date columns with your review details, as with flags. A local `date` override
replaces the whole date object, so include its storage, format, and timezone.

Audit creation dates are different from journey dates, trip start dates, invoice
issue dates, and payment dates. Add their specific meanings to the corresponding
table column entries. Do not map every request containing "yesterday" to
`createdon`. Text sorting does not provide chronological order for DD-MM-YYYY
dates, and mixed/invalid strings must fail closed in the later execution layer.
No customer values have been sampled to verify uniform storage formats.

## 6. Add company terminology and approved metrics

Edit [glossary/business_terms.yaml](glossary/business_terms.yaml) for terms and
synonyms. The document shape is `terms: {term_name: definition}`. Each definition
supports description, aliases, related_tables, and the same review fields.

Edit [metrics/metrics.yaml](metrics/metrics.yaml) for formulas. Start with a draft
until the definition is agreed:

```yaml
metrics:
  transport_revenue:
    business_name: Transport Revenue
    description: 'Define exactly what revenue includes and excludes.'
    aliases: [transport revenue]
    expression: ''                    # Fill only after agreeing on the formula
    required_columns: []              # Exact table.column references
    required_filters: []              # Approved row-level filters
    verified: false
    source: manual
    reviewed_by: null
    reviewed_on: null
```

Your actual schema has `trip.revenue`, `tripinvoice.totalamount`, and
`tripinvoice.amountpaid`. Choose the company's intended meaning rather than
treating them as interchangeable. Confirm tax, discounts, cancellation rules,
date basis, and whether totals are at trip or invoice grain. A `required_filters`
entry has `column`, `operator`, and `value`; list it only when approved.

The current validator checks metadata structure, review provenance, declared
identifiers, and scope. It does not yet parse metric formulas or example SQL;
reviewed formulas/examples still need deterministic SQL validation in the later
planner/validator milestones. No formulas or queries execute from these files.

## 7. Add only missing logical joins

Edit [relationships/logical_relationships.yaml](relationships/logical_relationships.yaml)
only for expert-approved relationships missing from the physical FK catalog.
Each entry has `from: {table, column}`, `to: {table, column}`, `relationship`
(one_to_one, one_to_many, many_to_one, or many_to_many), `type: logical`, and the
review fields.

These joins are already recorded as physical foreign keys and need no manual
duplication. The raw catalog retains joins involving excluded document tables;
those tables and joins are unavailable to approved reports while excluded:

```text
trip.driver                    -> tdriver.tdriverid
trip.vehicle                   -> tvehicle.tvehicleid
tdriverdocuments.tdriverid      -> tdriver.tdriverid
tvehicledocuments.tvehicleid    -> tvehicle.tvehicleid
tripinvoice.tripid             -> trip.tripid
tripinvoiceitem.invoiceid      -> tripinvoice.invoiceid
```

`tvehicle.driver` is VARCHAR and has no declared FK to `tdriver`; do not invent
an ID join from its name. Confirm the actual application relationship before
adding a logical edge. Never replace missing relationships with name similarity.

## 8. Validate after each small batch of edits

From the repository root, with the project's virtual environment active:

```powershell
python scripts/validate_metadata.py
python -m pytest tests/unit/test_metadata.py -q
```

`status: valid` means the documents are structurally consistent with the raw
catalog. It does not mean every draft is verified or ready for SQL execution.
Initially, `approved_tables` and `approved_column_count` are empty/zero; after
your reviews they show what future retrieval may use. Excluded tables remain
excluded even if an old table file is marked verified.

To create templates for newly included tables after changing scope:

```powershell
python scripts/create_metadata_templates.py
```

The generator skips existing files and preserves manual edits. It does not
automatically update older table files after a schema change; re-extract and
review the differences. Missing or renamed identifiers cause validation errors.

Add expert-approved SQL examples to [examples/verified_queries.yaml](examples/verified_queries.yaml)
later, with question, sql, related_tables, tags, and review details. Use sanitized
examples and keep drafts unverified. The next useful input is a short list of
the first reports you want, along with the business date and metric definitions
for those reports.
